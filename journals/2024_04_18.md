	- `core/shard`shard的实现：管理负责的匹配类型，各自shard通过锁抢占匹配类型，实现高可用
		- `shard.go`
			- `LockRentTime = int64(10) // 锁的租约时间，超时未续租会被其他节点抢占`，可以通过修改mongo锁记录的LRTS，使得`当前时间 - LRTS > LockRentTime`，触发锁失效，发起重新抢锁
			  id:: 6620c48a-0ed4-49a0-8dd1-73a8e141ad21
			  ```go
			  cursor, err := s.MongoManager.GetAllAvailableLock(LockRentTime)
			  
			  //	获取所有未被接管或者超期的锁
			  func (mm *MongoManager) GetAllAvailableLock(offset int64) (*mongo.Cursor, error) {
			  	filter := bson.M{
			  		"$or": []bson.M{
			  			{LRTS: bson.M{"$lt": time.Now().Unix() - offset}},
			  			{LRTS: bson.M{"$exists": false}},
			  		},
			  	}
			  	return mm.LockColl.Find(context.Background(), filter)
			  }
			  ```
			- `LockTickTime = 8 * time.Second // 抢锁周期`，让一个shard卡住LockTickTime时间（或者直接删掉pod，锁的归属登记用的是pod name），就能导致错过一个抢锁周期
			  id:: 6620c8e5-13ba-4086-a2ee-671a0c04d97c
			- `LockMinUnusedShard = 2 // 有超过该数量的RUNNING shard未获取到任何锁，且本shard已经有锁时，本shard不再获取锁`，保障锁分布均衡的策略，目前看没有特别构造边界异常的必要
			- `LockMaxPercentShard = int64(2) // 单shard获取锁的数量不能超过平均锁数量的一定比例，如总共有十个锁，五个节点，则单个节点不能超过2 * 该值的数量`，还是保障锁分布均衡的策略。这两个负载均衡策略有没有可能简化，降低对mongo查询全局锁信息的依赖❓
			- `LockLongTimeInactive = 10 * time.Minute // 超过该时间队列数据未产生变化时，会释放并删除掉锁`，清除不活跃的锁，目前看触发边界异常问题也不大
			- `LockHighAvailableTime = 60 * time.Second // 超过该时间未被任何节点接管的锁，抢锁时会忽略任何条件立刻接管`，作为兜底逻辑，什么情况下会触发这个场景：旧shard都挂掉了❓
